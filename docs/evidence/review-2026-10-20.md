## Blocking

### B1. Unbounded per-entry crypto in `jwe.Decrypter.DecryptJSON` and `jws.JSON.Verify` (CPU amplification)

- `pkg/jwe/json.go:356-376` (the recipient loop), `pkg/jwe/json.go:211-219` (no recipient-count cap in ParseJSON)
- `pkg/jws/json.go:296-309` (the signature loop), `pkg/jws/json.go:203-209` (no signature-count cap)

**Failure path.** `DecryptJSON` tries every recipient whose `alg` is allowed, and each try is a private-key operation (RSA-OAEP decrypt, or an ECDH plus key unwrap). Nothing limits how many recipients a message may carry. Measured in a probe: a 977 KB general-JSON JWE with 2,500 `RSA-OAEP` recipients (all-zero encrypted keys, `enc` in the shared unprotected header) took **2.9 s of CPU** with a `Decrypter{Key: rsa2048}` before it returned `ErrDecryption`. A 1 MB request body is a common server limit, so one request costs about 3 s of server CPU. `jws.JSON.Verify` has the same shape: one signature check per entry whose alg suits the key. That is cheaper per entry (about 50-100 µs for ES256), but it is still unbounded.

The module already treats this class as a bug elsewhere. `jwt.MaxCandidateKeys` exists so that "a key source that returns many keys cannot be used to make a verifier do unbounded work" (`pkg/jwt/verifier.go:30-33`), and jwtchain caps links at 8.

**Fix.** Add `MaxRecipients` / `MaxSignatures` (default 8 or 16, mirroring `MaxCandidateKeys`). Either refuse larger objects in `ParseJSON` (`ErrMalformed` / `ErrFormat`), or cap how many entries `DecryptJSON` / `Verify` will attempt. Add a negative test that builds an object over the cap.

## Low

### L1. Base64url decoding accepts CR/LF, so compact JWS/JWE strings are malleable

- `internal/base64url/base64url.go:16,26-31`. `base64.RawURLEncoding.Strict()` still skips `\r` and `\n`; the `encoding/base64` docs say so explicitly.

**Failure path (verified by probe).** Take a valid compact JWS and insert `"\n"` into the payload segment and `"\r\n"` into the signature segment. `jws.Parse` accepts the result and `Signature.Verify` returns nil. The payload is re-encoded for the signing input (`jws.go:291-292`), so the newline disappears, and the signature bytes decode the same. The signature still covers the same content, so this is not a forgery. It does give the same token a second string form. That breaks anything keyed on the raw string: replay caches, revocation deny-lists, or "seen token" logs built on `jws.Parse` or `jwe.Parse`. It also contradicts the package docs, which promise one valid encoding per value (`base64url.go:5-6`).

The same decoder sits behind `jwe.Parse` (`jwe.go:151-163`), `jws.ParseJSON` and `jwe.ParseJSON` (a JSON string can carry `\n`), `jwk` members (`keys.go:235`), `ni.Parse` (`ni.go:373`) and `holderOf` jkt (`jwtchain/state.go:295`). `jwt.Verifier` (`verifier.go:521-535`) and `jwtchain.parseToken` (`chain.go:357-371`) re-encode and compare, so they are protected. `dpop.Verifier` uses `jws.Parse` without that check, but its replay key is `jti`, so DPoP is unaffected.

**Fix.** In `base64url.Decode`, reject any input containing `\r` or `\n` (or re-encode and compare). That fixes every caller at once. Add a negative test.

### L2. ECDSA signature malleability contradicts the jwt.Verifier "one string form" claim

- `pkg/jws/jws.go:746-757`. `ecdsa.Verify` accepts both `s` and `n-s`.
- `pkg/jwt/verifier.go:518-520`. The comment says canonicalization means "one signed token has exactly one string form and caches keyed by the raw token cannot be bypassed".

**Failure path (verified by probe).** Replace `s` with `n-s` in any ES256/384/512 token. The new canonical string verifies. A deployment that revokes or deduplicates ES* JWTs by raw string can be bypassed by whoever holds one valid token. jwtchain already documents this (`chain.go:354-356`, "name tokens by jti"). The jwt docs do not.

**Fix.** Rejecting high-S would break interop: Go and most signers emit it about half the time. Instead, correct the jwt.Verifier comment and add a doc note on `Verifier` and `jws.Signature.Verify` that replay and revocation must key on `jti` (or on a hash of the decoded header, payload and normalized signature), never on the raw string.

### L3. jwtchain: a root with a foreign or empty `cnf` passes the AllowBearer gate with `Grant.Holder == ""`

- `pkg/jwtchain/state.go:99-113` and `pkg/jwtchain/verify.go:272`.

**Failure path (verified by probe).** Root `cnf` is `{"x5t#S256":"..."}`, or `{}`, or `{"jkt":..., "x5t#S256":...}`. Then `s.confirmation != nil` and `s.holder == ""`. `VerifyChain` therefore does not return `ErrBearer`, and the grant comes back with an empty `Holder`. The doc on `Policy.AllowBearer` says the default exists "so a verifier that checks proof of possession against Grant.Holder is never handed an empty thumbprint", and the package doc says to pass `Grant.Holder` as `dpop.Request.Thumbprint`. An empty `dpop.Request.Thumbprint` means "no binding required" (`dpop/verifier.go:432`). An mTLS-bound or oddly-bound root therefore becomes a bearer token for a jwtchain+DPoP verifier. This needs the issuer to mint such a `cnf`, hence Low. The `Grant.Holder` comment does mention "check Confirmation", but the AllowBearer promise is broken as written.

**Fix.** In `VerifyChain`, refuse with `ErrBearer` when `s.holder == "" && !p.AllowBearer`, whatever `s.confirmation` holds. If foreign bindings are wanted, add an explicit opt-in such as `AllowForeignConfirmation`. Add negative tests for `{}`, mTLS-only and mixed `cnf` roots. Today only links are tested for these ("cnf two members", "cnf mTLS only").

### L4. `dpop.MemoryReplayCache`: anyone can fill it, and eviction is O(n) per request when full

- `pkg/dpop/replay.go:528-536`.

**Failure path.** DPoP proofs are self-signed. At an endpoint that verifies proofs without a `Thumbprint` or `AccessToken` (for example a token endpoint), an unauthenticated client can mint fresh-jti proofs with its own key until the cache holds `max` entries. From then on, **every** client gets `ErrReplayCacheFull` for up to `MaxAge+Leeway` (5.5 min by default). Failing closed is deliberate and documented. But the cost is O(max) per request: each `Seen` call scans the whole map while full, so the attack also burns CPU.

**Fix.** Document the global fill risk prominently. Better: evict expired entries amortized (a min-heap or time buckets) rather than with a full scan, and suggest partitioning by key thumbprint or rate-limiting per client ahead of `Verify`.

### L5. A JWK Set with one unsupported key makes the whole set unusable

- `pkg/jwk/jwk.go:146-159` (`Set.Validate`), `pkg/jwk/jwkhttp/jwkhttp.go:288` and `pkg/jwt/verifier.go:134-137` (`KeysFromSet`).

**Failure path.** An IdP publishes an Ed448, secp256k1, ML-DSA (`AKP`) or other not-yet-understood key next to its RS256 key. `FetchSet` then fails, `jwkhttp.Keys` serves stale keys until MaxStale and then fails, and every token verification fails. RFC 7517 §5 says implementations SHOULD ignore JWKs whose `kty` they do not understand. This is an availability risk, not a forgery.

**Fix.** In `KeysFromSet` (and `Set.Validate` as called by `FetchSet`), skip keys with an unknown `kty` or `crv` instead of failing. Keep refusing private or `oct` keys and malformed keys of known types.

## Nit

1. **`jwt.Verifier` drops error chains.** `verifier.go:227` wraps the jws error with `%v`, so `errors.Is(err, jws.ErrAlgorithm)` is false. `verifier.go:272` wraps the key-source error with `%v`, so `errors.Is(err, context.Canceled)` and `errors.Is(err, jwkhttp.ErrFetch)` are false. Use `%w` for the cause.
2. **`jwt.Verifier` reports expiry before the signature check.** The early `checkTimes` runs pre-signature (`verifier.go:266`), so a forged token with a past `exp` gets `ErrExpired` rather than `ErrSignature`. No security impact; the classification is just misleading. Document it or reorder.
3. **`jwt.Verifier` does not enforce `cnf`.** A PoP-bound token passes as bearer unless the caller checks `ConfirmedThumbprint`. Consider an opt-in `RequireConfirmation` field, or a doc warning on `Verifier`.
4. **`jwe.Parse` splits before counting.** `jwe.go:179` calls `strings.Split` before checking the part count, so a 1 MB string of dots allocates a 1M-element slice. Use `strings.Count(compact, ".") != 4` first, as jws does.
5. **`enc`, and JWS `alg`, may sit in unprotected headers.** RFC 7516/7515 allow it, and it is not exploitable here: CEK lengths, and AEAD/HMAC checks under a key the attacker does not know, prevent useful substitution. Still, refusing `enc` outside the protected header (or a doc note) would remove cross-algorithm key reuse between A256GCM and A128CBC-HS256 for KW recipients.
6. **`jwthttp.BearerToken` reads only the first Authorization header.** It uses `r.Header.Get`, so multiple Authorization headers are silently reduced to the first. `dpophttp.AccessTokenFromRequest` requires exactly one. Align them.
7. **jwtchain with `RootKey` does not require a root `exp`.** A link-less chain from a root without `exp` never expires (links always carry `exp`). `RootVerifier` requires it. Document this next to RootKey, or require `exp` in `rootState` unless opted out.
8. **Some errors carry no sentinel.** The signing and minting errors of `jwt.New`, the non-broadening refusals of `jwtchain.Derive`, and `dpop.TargetURI` errors are plain `errors.New` or `fmt.Errorf`. They are not verification paths, but `errors.Is` cannot classify them. `thumbprint.FromPublicKey` returns `jwk.ErrInvalidKey`, not `thumbprint.ErrInvalidKey`.
9. **`jwkhttp` checks for loopback by name.** `checkURL` accepts `http://localhost` by name, which `/etc/hosts` could point elsewhere. An https URL may redirect to any https host. The URL is operator-configured, so the impact is minimal.
10. **Gaps in negative tests:**
    - no truncated or oversized JWE tag test; the code checks exact length (`content.go:79,132`), but only bit-flip tampering is tested;
    - no high-S or CR/LF malleability tests (see L1 and L2);
    - no test of JSON objects with many recipients or signatures (see B1);
    - no test of a jwtchain root with foreign or empty `cnf` (see L3).

## Verified correct (evidence for the rung)

**JWS (RFC 7515, 7797)**
- `alg: none` never verifies (`jws.go:433-435`). It is refused for signing unencoded payloads (`:348`) and in the JSON serialization (`json.go:109,249`). `jwt.New` refuses to mint it (`jwt.go:97`). jwt, dpop and jwtchain verifiers refuse it independently.
- HMAC versus asymmetric key confusion is impossible. HMAC takes only `[]byte`/`string` (`jws.go:506-513`). RSA, PS, ES and EdDSA verification take only their concrete public-key types (`:591,635,731,788`). An RSA public key can never act as an HMAC secret, and a `[]byte` can never verify an RS/ES token. The jwt default allowlist is asymmetric-only, and HS* must be listed explicitly (`verifier.go:39-44`). `KeysFromSet` refuses `oct` and private keys (`verifier.go:122`).
- The RSA floor is 2048 bits for sign and verify (`jws.go:806-828`), and JWE RSA-OAEP keeps the same floor. JWK caps the modulus at 8192 bits and the exponent at an odd value in [3, 2^31-1] (`keys.go:340-369`), which bounds verification cost for attacker-supplied keys (DPoP and jwtchain `jwk` headers).
- RSA-PSS uses salt length equal to the hash length on both sign and verify (RFC 7518 §3.5).
- ECDSA: each alg is pinned to its curve (`jws.go:658-680`). The signature must be exactly 2×coordinate size in fixed-width R||S (`:741`), and r = 0, s = 0 or out-of-range values are rejected by `ecdsa.Verify`. DER from signers is converted strictly (`:713-727`). High-S is accepted (L2).
- EdDSA requires a 32-byte key. Go's `ed25519.Verify` rejects non-canonical S.
- Duplicate header or claim member names are refused at any depth, with nesting capped at 64 (`strictjson.go`). Invalid UTF-8 is refused before `encoding/json` can substitute U+FFFD. Trailing data is refused.
- `crit` (§4.1.11):
  - it must be a non-empty array of strings;
  - it may not name standard parameters;
  - every name must be understood and present;
  - in JSON it is accepted only in the protected header.
- jwt.Verifier refuses any `crit` name not in `Verifier.Critical`, and refuses `b64` in a JWT.
- `b64` (RFC 7797) must be boolean and listed in `crit`. `b64:false` is accepted only via `ParseDetached`, and is refused in Parse, the JSON serialization and JWTs.
- The signing input uses the received protected-header segment. Payload mutation after Parse breaks verification.

**JWT (RFC 7519, RFC 8725)**
- `Verifier.check` requires `Keys`, and requires `Issuer` and `Audience` unless they are waived by the named `AnyIssuer` / `AnyAudience` fields. `exp` is required unless `AllowNoExpiry` is set.
- The size cap (16 KiB) is checked before parsing. Canonical base64url is required. `typ` is checked against an allowlist: case-insensitive, optional `application/` prefix, default "JWT" or absent. An empty string `typ` is refused.
- A non-string or empty `kid` is refused. At most 8 candidate keys are tried. Keys are filtered by `kid` and `alg`.
- `exp`/`nbf`/`iat` have leeway (default 30 s). Future `iat` is refused. NaN, Inf, negative and year-10000+ values are refused. `aud` may be a string or an array of strings, and null or non-string `aud` is refused. Times are re-checked after the key fetch.
- `cnf`: `ConfirmedThumbprint` requires `cnf` to hold `jkt` as its sole member. `act`/`may_act` (RFC 8693): nesting capped at 32, `sub` required, and `exp`/`nbf`/`aud` refused inside `act`. `may_act` cannot nest.
- `jku` / `x5u` / `x5c` are never followed. Neither jwt nor jwkhttp reads token header URLs.

**JWE (RFC 7516, 7518)**
- RSA1_5, PBES2, A*GCMKW and `zip` are not implemented and refused with `ErrUnsupported`, both compact and JSON, so there is no Bleichenbacher oracle, no PBES2 iteration DoS and no decompression bomb.
- ECDH-ES rejects invalid curves. `epk` goes through `jwk.PublicKey` → `ecPoint`, which validates the point with `crypto/ecdh` NewPublicKey (on-curve, not identity), and the coordinate length is capped. `epk` must be EC/OKP with no private members, and its curve must equal the recipient's. X25519 low-order points fail in `ECDH()` → `ErrDecryption`. The Concat KDF uses `enc` (direct) or `alg` (KW) as AlgorithmID, length-prefixed apu/apv, and keydatalen in bits.
- RSA-OAEP failure continues with a random CEK (RFC 7516 §11.5). The error is a uniform `ErrDecryption` after structure acceptance.
- AES-KW checks the RFC 3394 IV in constant time, length ≥ 24 and a multiple of 8. The unwrapped CEK length must match `enc`.
- GCM: 12-byte IV and 16-byte tag exactly. CBC-HMAC: MAC key first, enc key second (§5.2.2.1), HMAC over AAD‖IV‖C‖AL verified in constant time before padding, tag length exact (no truncation), constant-time padding check.
- AAD is the received protected segment (plus `.aad` in JSON). Disjoint header names, `enc` shared by all recipients, and `dir`/`ECDH-ES` single-recipient are enforced. A `[]byte` key requires an explicit `Algorithms` list.

**JWK, thumbprint, jwkhttp**
- `IsPrivate` covers d/p/q/dp/dq/qi/oth/k. Private keys are refused in published sets (`KeysFromSet`), in the DPoP `jwk` header, in jwtchain link `jwk` and `cnf.jwk`, and in JWE `epk`. Duplicate `kid` in a set is refused.
- The private-key parser checks public/private consistency, two primes only, and runs `rsa.Validate`.
- RFC 7638 thumbprints use the required members in lexicographic order and refuse values that need JSON escaping. `FromPublicKey` canonicalizes via `PublicValue`, which DPoP and jwtchain use, so spelling variants (trimmed coordinates, CR/LF) cannot change a binding.
- jwkhttp:
  - https only, or http to loopback; no userinfo;
  - redirects are re-checked and an https→http downgrade is refused;
  - 1 MiB body cap and 15 s fetch timeout;
  - refetch on an unknown kid is rate-limited (≥ 5 s);
  - single-flight fetches, and the mutex is never held across I/O;
  - bounded stale serving.

**DPoP (RFC 9449 §4.3)**
- 8 KiB cap. `typ` must be `dpop+jwt`. The alg must be asymmetric and allowlisted. The `jwk` header must be public and is parsed with point and size validation. The signature is checked with that key.
- `jti`/`htm`/`htu`/`iat` are required. `htm` is compared exactly. `htu` is normalized per RFC 3986 §6.2.2/6.2.3 on both sides: query and fragment dropped, userinfo refused, IPv6 zones refused, default port removed, dot segments removed.
- The `iat` window is MaxAge (5 min) in the past and Leeway (30 s) in the future. The nonce is compared exactly in constant time, or via `CheckNonce`. `ath` is required and compared in constant time when an access token is presented. `jkt` is compared in constant time against the canonical thumbprint.
- The replay check runs last, so failed proofs do not burn a jti. Its entries expire at iat+MaxAge+Leeway, which covers the whole acceptance window. The cache is atomic under its mutex.
- `BoundThumbprint` requires `cnf` to hold `jkt` alone. `dpophttp.FromRequest` refuses zero or multiple DPoP headers.

**jwtchain (attenuation)**
- A link cannot broaden its parent:
  - `aud` must be a subset when the parent names audiences, and an empty `aud` is refused;
  - `scope` must be a subset, and a scopeless parent cannot gain scope;
  - scope tokens are parsed strictly per RFC 6749 §3.3, and tab-split scopes are a tested regression;
  - `exp` is required and ≤ the parent's;
  - `nbf` takes the maximum;
  - caveats only accumulate;
  - `sub` and any claim outside the fixed allowlist are refused;
  - `iss` must equal the signer's RFC 9278 URN.
- Holder binding: a link must be signed by the key whose canonical thumbprint equals the parent's holder (from `cnf.jkt`, a 32-byte check, or from `cnf.jwk`, which must be a public signing key). A link `cnf` must hold exactly one member. A link without `cnf` ends the chain.
- Structure: `typ` `chain+jwt`, `prh` in `crit`, and a parent digest by ni (sha-256/384/512 only, full length, constant-time compare). The embedded `prt` must be one token and is digest-checked. Every token must be canonical base64url. A root cannot be a link, by `typ` or `prh`.
- Limits: 8 links and 64 KiB by default. The size is checked before splitting, and the link count both before and during the walk. Expired chains are refused before any signature work. Link algorithms are asymmetric-only even if `Limits.Algorithms` lists HS* or none. A nil `Caveat` refuses any caveat. Bearer leaves are refused by default (but see L3).
- `Derive` re-applies the verifier's rules to the link it mints.

**ni (RFC 6920)**
- Scheme is case-insensitive "ni". Query and fragment are refused. Only full-length sha-2 and sha-3 algorithms are accepted, and truncated ones are refused. Padding is refused and the digest length must be exact. `Matches` compares in constant time.

**Error design**
- Every verification package exposes sentinels, and its errors match with `errors.Is`:
  - jws: `ErrFormat`, `ErrSignature`, `ErrAlgorithm`, `ErrNoValidSignature` (which also matches `ErrSignature`);
  - jwt: `ErrInvalidToken` plus `ErrFormat`, `ErrSignature`, `ErrExpired`, `ErrNotYetValid`, `ErrClaims`, and the non-refusal `ErrKeysUnavailable`;
  - jwe: `ErrMalformed`, `ErrUnsupported`, `ErrNotAllowed`, `ErrDecryption`;
  - jwk: `ErrFormat`, `ErrInvalidKey`;
  - jwkhttp: `ErrInsecureURL`, `ErrFetch`;
  - dpop: `ErrInvalidProof`, with `ErrUseNonce`, `ErrReplay` and `ErrBinding` each also matching it, plus `ErrReplayCacheFull`;
  - jwtchain: `ErrFormat`, `ErrVerification`, with `ErrBroadens`, `ErrCaveat` and `ErrBearer` each also matching it;
  - also ni `ErrFormat`, the header errors and jwa `ErrUnknownAlgorithm`.
- Messages contain no key material. The only gaps are listed in Nit 1 and Nit 8.

**Negative tests present** (on origin/main) for:
- alg none, key confusion, small RSA keys, invalid curves and private-JWK headers;
- duplicate members, `crit` and `b64` handling;
- RSA1_5, PBES2 and zip refusal;
- JWE tampering per segment, with a uniform `ErrDecryption`;
- `jku`/`x5u` not followed, plus jwkhttp redirect, insecure URLs and the size cap;
- DPoP htu, iat, nonce, ath, replay and binding;
- jwtchain broadening of aud, scope and exp, subject change, unknown claims, the issuer, `cnf` shape, caveats, bearer, digest, `typ`, `crit`, order, symmetric links and oversize;
- jwt size, type, issuer, audience and expiry.

The gaps are listed in Nit 10.

**B1.** `jwe.ParseJSON` caps recipients and `jws.ParseJSON` caps signatures at 16. The check runs right after syntax detection and before any decoding or crypto. A flattened object counts as one entry. The probe with 2,500 recipients is now refused in 0.13 s, where it previously cost 2.9 s.

Residual (Nit): `DecryptJSON` and `JSON.Verify` do not repeat the cap, so a caller who builds a `JSON` value by hand from untrusted data is not bounded. Consider checking `len(...) > max` in `check()` and in `Verify`.

**L2.** `jws/doc.go`, `jwt/doc.go` and the `canonical` comment now say that ES* signatures are malleable and that caches must key on `jti`. The behaviour is unchanged by design.

**L3.** The gate is now `s.holder == "" && !AllowBearer`, so these roots return `ErrBearer`, which the probe confirms:
- an empty `cnf`;
- an mTLS-only `cnf`;
- a mixed `jkt` plus `x5t#S256` `cnf`.

Roots bound by `jkt` alone or by `jwk` are unaffected, and so is `Derive`. With the default policy, `Grant.Holder` is now never empty.

**L4.** `earliest` is maintained as a lower bound on the live entries' expiries:
- it is set on insert when the cache is empty or the new expiry is earlier;
- it is recomputed exactly on each scan;
- replacing an expired same-jti entry keeps it a lower bound.

It is consulted only to return `ErrReplayCacheFull` early, and it is never used to accept a proof. The duplicate-jti check still runs first, unconditionally. So if the bound is wrong in either direction, the only effect is an extra scan or a refusal; it can never let a replayed proof through. The cache fails closed, and a backwards clock also fails closed. The differential test found identical `(seen, full)` results to the original algorithm on every step of 3,000 random traces, including expiries in the past and jti reuse.

Residual cost: while the cache is full, a scan happens about once per expiry event rather than once per request. That is bounded and acceptable.

**L5.** For a `kty` that is a string the module does not know (for example `AKP`, used by ML-DSA, or `ec` in lowercase), the key is now skipped in both `Set.Validate` and `KeysFromSet`. A set made only of such keys is refused. Keys with a **known** `kty` are never skipped:
- a bad point, a non-string `kty` or malformed members still fail the whole set (probed);
- in `KeysFromSet`, the private-key and `oct` refusal runs **before** the unknown-kty skip, so an unknown-kty entry that carries `d` is still refused.

### jwt.Verifier: time checks moved after the signature (2f227f9)

The change does not let an attacker force more key-source lookups.

Before it, an unsigned token with a past `exp` was refused without a lookup. But an attacker could always reach `Keys.Keys` with a forged token carrying a future `exp`, which has the same cost and the same `kid` control. So the pre-signature expiry check never limited what an attacker could make the verifier do; it only saved work on honest expired tokens.

`jwkhttp.Keys` bounds the cost in any case:
- the set is cached for its TTL (at least 1 minute);
- a refetch triggered by an unknown `kid` happens at most once per `RefetchInterval` (at least 5 s), across all callers;
- fetches are single-flight, and callers holding a usable set return immediately.

The per-token signature work is still capped at `MaxCandidateKeys` (8). The only new cost is up to 8 signature checks on a forged expired token, which a forged unexpired token already cost.

The claims are still decoded and bounded before the lookup, and `exp` is still required and is now checked after the signature. The `%w` wrapping of the jws error and the key-source error now makes `errors.Is(err, jws.ErrAlgorithm)` and `errors.Is(err, context.Canceled)` work.

Nit: a `KeySource` error that itself wraps `jwt.ErrInvalidToken` would now make an unavailable-keys error match `ErrInvalidToken`. No source in this module does that. A one-line doc note on `KeySource` would cover it.

### Fuzz target soundness (70a536e)

- **jwt FuzzVerify** has a sound oracle. Any accepted token must have a signing input (`header.payload`) that the test key really signed. That correctly allows the high-S signature variant and nothing else. It also checks `String() == input` and that every error wraps `ErrInvalidToken`; the fixed `Keys` source cannot return `ErrKeysUnavailable`.
- **jwtchain FuzzVerify** checks invariants that match the fixture root exactly:
  - subject `alice`;
  - scope ⊆ {read, write, delete};
  - audience ⊆ {api, admin} and containing `api`;
  - expiry ≤ root + 1 h;
  - only accepted caveats;
  - a non-empty `Holder`, which L3 makes valid.

  The fuzzer cannot sign, so the target mostly exercises parse and recombination (dropping links, reordering, duplicating, embedding). That is the right attack surface for an unkeyed fuzzer, and the oracles are sound.
- **jws FuzzParseCritical, header FuzzValidateCriticalHeaders** restate RFC 7515 §4.1.11 independently of the implementation. They also cross-check that `Parse` and `ParseCritical` agree on the payload, and that a header which passes fails again with no understood extensions. Sound.
- **dpop FuzzBoundThumbprint, jwt FuzzActors** check that the `jkt` must be the sole member of `cnf`, and that `act` survives a round trip and stays within `MaxActors`. Sound.
- **dpophttp and jwthttp header fuzzers** check single-header and scheme handling. Sound, though the token-shape check covers only space and tab. CR/LF cannot reach a server through net/http, so this does not matter.

### New findings

- **R1 (Low, availability, L5 remainder).** A key with a known `kty` but an unsupported `crv` still fails the whole set. Examples: `{"kty":"EC","crv":"secp256k1"}` and `{"kty":"OKP","crv":"Ed448"}`. Both were probed: `Set.Validate` and `KeysFromSet` return `unsupported EC curve` / `unsupported OKP curve`. These are exactly the provider keys L5 cited. Treat a string `crv` that is not recognized under EC or OKP as "unsupported, skip", exactly like an unknown `kty`. Keep refusing malformed members and off-curve points on supported curves. Skipping is safe, because a skipped key can never verify anything.
- **R2 (Nit).** `IsPrivate` knows only RFC 7518/8037 member names, so an unknown-kty key that carries private material under a new name (for example AKP `priv`) is skipped silently rather than refused. The module never uses the key, so this is not a hole. But "a set holding a private key is refused" holds only for known key types; say so in the docs.

### Remaining security issues

There is **no remaining Blocking issue**. One **Low** remains: R1, an availability issue that fails closed with no forgery impact. Everything else is a Nit.
